## 1. Ringkasan

### Tujuan Bisnis

Modul Document Management System menjadi repository dokumen terpusat untuk seluruh aktivitas HR, legal, dan administrasi perusahaan, sehingga:

- dokumen tidak tercecer di lokal user atau chat
- akses dokumen sensitif bisa dikontrol per role dan per kepemilikan
- dokumen memiliki jejak audit yang jelas
- dokumen kadaluarsa bisa dimonitor
- proses tanda tangan digital bisa dilacak

### Masalah yang Diselesaikan

- dokumen karyawan tersebar di banyak tempat
- tidak ada versioning yang jelas saat kontrak atau policy direvisi
- akses ke KTP, NPWP, kontrak, dan dokumen legal belum terkontrol rapi
- tidak ada monitoring expiry untuk kontrak, sertifikat, lisensi, atau policy lama
- belum ada alur standar untuk e-sign dokumen HR

## 4. Status

### Status Dokumen

- `Draft`
- `Uploaded`
- `Pending Review`
- `Pending Signature`
- `Active`
- `Expired`
- `Rejected`
- `Superseded`
- `Archived`

### Transisi Status

1. `Draft` -> `Uploaded`
2. `Uploaded` -> `Pending Review`
3. `Pending Review` -> `Pending Signature` atau `Active` atau `Rejected`
4. `Pending Signature` -> `Active`
5. `Active` -> `Expired` jika lewat tanggal expiry
6. `Active` -> `Superseded` jika ada versi baru
7. `Active` atau `Superseded` -> `Archived` jika diarsipkan sesuai policy

### Locking Rule

- dokumen yang sudah `Active` dan sudah di-sign tidak boleh diedit isi filenya
- koreksi dilakukan dengan upload versi baru
- metadata tertentu seperti `tags` atau `notes` masih bisa diedit role tertentu jika policy mengizinkan

## 5. Alur Utama

### A. Upload Dokumen Employee

1. HR atau employee membuka halaman upload dokumen.
2. User memilih kategori, owner, company, judul, jenis dokumen, dan file.
3. Sistem memvalidasi tipe file, ukuran, company scope, dan hak upload user.
4. File diunggah ke storage.
5. Metadata dokumen dibuat dengan status `Uploaded`.
6. Jika kategori butuh review, status berubah `Pending Review`.
7. Jika tidak butuh review dan tidak butuh tanda tangan, status langsung `Active`.
8. Sistem mencatat audit log dan document access log awal.
9. Jika ada expiry date, sistem menjadwalkan reminder.

### B. Upload Revisi / Versi Baru

1. User memilih dokumen aktif yang mau direvisi.
2. Sistem membuat record versi baru dengan referensi ke versi sebelumnya.
3. Dokumen lama tetap tersimpan dan berubah menjadi `Superseded` setelah versi baru aktif.
4. Akses history version tetap tersedia untuk role yang berhak.

### C. E-Sign Dokumen

1. HR atau Legal membuat dokumen dengan `signed_required = true`.
2. Sistem mengirim request signature ke signer yang ditentukan.
3. Status dokumen menjadi `Pending Signature`.
4. Signer membuka preview, membaca, lalu menandatangani.
5. Sistem menyimpan signature record dan timestamp.
6. Jika seluruh signer selesai, dokumen berubah `Active`.

### D. Monitoring Expiry

1. Sistem mengecek dokumen yang punya `expiry_date`.
2. Pada H-30 dan H-7, notifikasi dikirim ke owner dan HR.
3. Jika melewati tanggal expiry, status berubah `Expired`.
4. Role terkait bisa upload renewal document atau versi baru.

## 6. Alur Alternatif / Exception

### Reject

- reviewer menolak dokumen karena file salah, metadata tidak sesuai, atau dokumen blur/tidak valid
- status menjadi `Rejected`
- user mendapat alasan penolakan dan bisa upload ulang

### Cancel Signature

- HR/Legal membatalkan proses sign sebelum semua signer selesai
- status kembali ke `Pending Review` atau `Uploaded` tergantung policy

### Duplicate

- sistem mendeteksi file atau nomor dokumen sama pada owner dan kategori yang sama
- user diminta pilih: jadikan versi baru atau simpan sebagai dokumen terpisah

### Conflict

- dua user mengedit metadata bersamaan
- last update ditolak jika version token tidak cocok
- UI menampilkan pesan bahwa dokumen sudah diubah user lain

### Storage Failure

- jika upload file gagal setelah metadata sempat dibuat, dokumen masuk status `Draft` atau `Upload Failed`
- user diberi opsi retry

### Unauthorized Access

- user mencoba buka dokumen di luar scope
- sistem tolak akses
- percobaan tetap dicatat di access log / audit jika termasuk dokumen sensitif

## 7. Validasi dan Business Rules

### Validasi Upload

- file wajib ada
- ukuran file maksimum per kategori harus dikonfigurasi
- whitelist MIME type wajib diterapkan
- nama file disanitasi
- field owner wajib sesuai kategori

### Rule Kepemilikan

- dokumen employee wajib punya `owner_type = Employee`
- dokumen company wajib punya `owner_type = Company`
- dokumen group-wide wajib punya `owner_type = Group`

### Rule Versioning

- file dokumen aktif tidak boleh ditimpa langsung
- perubahan isi file selalu menghasilkan versi baru
- versi lama tidak dihapus kecuali policy retensi menyatakan boleh

### Rule Expiry

- kontrak, sertifikasi, lisensi, permit, policy tertentu wajib punya `expiry_date` atau `effective_date`
- status expiry berubah otomatis lewat job scheduler

### Rule Signature

- dokumen yang butuh legal evidence tidak boleh dianggap aktif final sebelum signer wajib selesai
- urutan signer bisa serial atau parallel, harus bisa dikonfigurasi

### Rule Company Scope

- HR company A tidak bisa melihat dokumen milik company B kecuali diberi akses eksplisit
- group-level doc bisa diwariskan view-only ke semua company dalam group

## 18. Catatan Implementasi

Supaya modul ini tidak berakhir jadi "sekadar upload file", implementasinya harus diperlakukan sebagai modul lintas sistem yang punya 4 aspek inti:

- repository file
- security dan access control
- legal workflow
- lifecycle management dokumen

Kalau salah satu aspek itu tidak didetailkan, modul akan terasa setengah jadi dan cepat menimbulkan masalah di produksi.
